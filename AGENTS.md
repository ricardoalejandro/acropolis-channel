# Guía de trabajo para Acrópolis Channel

El propietario define el objetivo; sus indicaciones actuales prevalecen sobre decisiones archivadas. Este AGENTS fija el marco general y las skills detallan procedimientos dentro de él. La guía local de Windows sólo permite llegar a estas instrucciones, no constituye otro nivel de mando.

## Inicio de cada sesión

El checkout de desarrollo está en WSL Ubuntu 24.04, `/home/rrojacam/projects/acropolis-channel`, repositorio `https://github.com/ricardoalejandro/acropolis-channel`, rama `main`. Codex Windows accede a él por `\\wsl$\Ubuntu-24.04\home\rrojacam\projects\acropolis-channel`; ejecutar comandos Linux con `wsl.exe -d Ubuntu-24.04 --cd /home/rrojacam/projects/acropolis-channel -- bash -lc 'COMANDO'`. Leer `docs/wsl-development.md` antes de preparar herramientas o ejecutar QA local. Las herramientas de Windows no deben generar dependencias ni builds en el checkout Linux.

Por decisión vigente del propietario, los cambios se desarrollan y revisan con servicios persistentes en este WSL y puertos fijos exclusivos: `https://localhost:17443` para la aplicación, `http://localhost:17480` para redirección HTTPS y `http://localhost:17425` para el buzón Mailpit. Todos se publican sólo en `127.0.0.1`; PostgreSQL y SMTP permanecen internos sin puerto del host. Usar `compose.local.yml`, proyecto `acropolis-channel-local`, mediante `python3 scripts/local-runtime.py up|stop|status|check|logs` (`up --no-build` reutiliza las imágenes locales) o el wrapper Windows `scripts/local-runtime.ps1` con esos comandos y `trust` adicional para la confianza del certificado. En PowerShell usar `up -NoBuild` para reutilizar imágenes; `--no-build` corresponde al helper Python. Sus variables `LOCAL_*` se generan privadamente en `.local/runtime/.env`; redes, base, keyring y PKI locales son propios y persistentes.

El correo local habilitado llega exclusivamente a Mailpit y permite probar los recorridos normales de confirmación sin credenciales ni entregas productivas. No copiar datos de producción, sembrar cuentas ni saltarse confirmación/MFA. El certificado web local es autofirmado, `CA:FALSE`, y se exporta a `.local/runtime/export/localhost.crt`; el wrapper Windows gestiona la confianza de ese certificado exacto en `Cert:\CurrentUser\Root` y se debe comprobar su instalación. La CA SMTP queda privada dentro del runtime local.

Al retomar, consultar `status` y comprobar `check` antes de volver a levantar servicios; conservar el runtime saludable. `up` desde Windows detiene y recrea sólo este proyecto, por lo que no se ejecuta para resolver únicamente la confianza TLS o actualizar instrucciones. Ante `NET::ERR_CERT_AUTHORITY_INVALID` de localhost, usar `./scripts/local-runtime.ps1 trust` y después `check`: la instalación está acotada y exige la hoja local validada en `CurrentUser/Root` y puede requerir confirmación inicial de Windows. Un `check` de WSL no acredita la confianza del navegador Windows. Leer la guía WSL para el diagnóstico; no regenerar PKI ni desactivar TLS para ocultar el error.

Desarrollo y producción comparten la fuente de aplicación y el Dockerfile; sus recetas y variables son distintas. Los cambios necesarios de código, recetas e instrucciones se revisan, validan y sincronizan en GitHub para poder retomarlos en otras sesiones. Las huellas instaladas, SHA, informes, estado observado y procesos pendientes pertenecen a la continuidad privada del entorno, no a reglas permanentes de AGENTS/skills.

El VPS conserva `/root/proyect/acropolis-channel` para certificación de publicación, producción y despliegue. Desde Windows conectar con `ssh -o BatchMode=yes -o StrictHostKeyChecking=yes vps`; el alias está configurado en esa máquina. Si la sesión ya corre en el VPS, operar directamente allí. Sincronizar código mediante Git, conservando el trabajo de ambos checkouts. `C:\proyectos\003.ACROPOLIS-CHANNEL` conserva la guía de acceso y artefactos de revisión.

Cuando el propietario solicite publicar más adelante, usar esa conexión VPS, las variables y secretos productivos que permanecen en el servidor, el gate correspondiente al riesgo del candidato y las imágenes certificadas allí. Levantar o actualizar localhost no activa ninguna publicación productiva; `compose.local.yml` y `.local/runtime/.env` no se usan en el VPS.

Leer este archivo y `.local/continuation-current.md` del entorno en uso para retomar. En WSL, `.local/` guarda continuidad y evidencias de desarrollo local. Para producción, consultar por SSH `.local/continuation-current.md`, `.local/vps-deployment.md`, `.local/last-active-deployment` y su manifiesto exclusivamente en el VPS; allí `.local/last-deployment` registra la última publicación verificada. No copiar secretos, backups o manifiestos productivos a WSL ni usar la continuidad local como prueba del runtime real. El HEAD de Git puede incluir documentación posterior al SHA desplegado. No confundir un commit publicado, QA aprobada y una versión en servicio.

Las skills canónicas están versionadas en `.agents/skills/acropolis-quality/SKILL.md`, `.agents/skills/acropolis-vps-deploy/SKILL.md` y `.agents/skills/acropolis-design/SKILL.md`. Cargarlas desde el checkout de trabajo y sincronizar sus cambios mediante Git para evitar copias divergentes. `docs/` y `scripts/` son relativos a ese checkout; `.local/` pertenece a cada entorno y no se sincroniza. Las rutas operativas de producción y la certificación previa al despliegue corresponden al VPS.

## Trabajo y arquitectura

- Revisar estado Git, rama y remoto; fetch y `git pull --ff-only origin main` cuando sea compatible. Conservar cambios, archivos no versionados y commits existentes; analizar divergencias sin reset hard, clean ni push forzado.
- Monolito modular ASP.NET Core / .NET 10 LTS, React 19 con TypeScript/Vite y PostgreSQL 18. SDK .NET 10 y Node 22 sólo en Docker, también durante desarrollo WSL; conservar Node 20 compartido del VPS. Leer `docs/architecture.md` y los documentos del módulo antes de cambiar contratos.
- Módulos actuales: Platform, Identity, Catalog y Subscriptions. Los módulos son dueños de sus schemas/historias; Application no depende de infraestructura ni se leen tablas internas de otro módulo. Migraciones sólo mediante runner y bloqueo exclusivo, nunca desde cada instancia web.
- Aplicar la skill acropolis-quality al programar o validar. Cada proceso requiere pruebas útiles de reglas, aplicación, PostgreSQL real, HTTP, interfaz, autorización y fallos; incluir concurrencia/idempotencia cuando corresponda. No añadir módulos vacíos o pruebas ficticias.
- Preservar las reglas Graphify existentes; `.graphify/` es generado y permanece fuera de Git/Docker. El código anterior en Node fue sustituido; no restaurar ese servidor ni GitHub Actions/credenciales dedicadas. Conservar el historial.

## Producto, identidad y diseño

- La versión publicada ya incorpora diseño adaptable, cuentas/MFA y catálogo editorial persistente. El objetivo de 100.000 cuentas es capacidad prevista, no una precarga inicial. Conservar las cuentas reales existentes; las cuentas sintéticas de volumen pertenecen exclusivamente a bases temporales de QA. El estado de cuentas y contenidos debe consultarse; no tratar datos vacíos como un fallo ni poblar producción con semillas QA.
- El correo Naperu es un proyecto independiente: fuente Git local en `/root/proyect/naperu-mail/source` y runtime privado en `/root/proyect/naperu-mail`. Mantener fuera de este repositorio sus recetas, webmail, scripts, pruebas y documentación operativa. Sus timers ejecutan operaciones certificadas en `.local/operations/current`; editar el HEAD de correo no cambia el servicio. Acrópolis conserva únicamente su cliente y guard de integración SMTP. Leer `docs/smtp-integration.md`. Mantener `IDENTITY_EMAIL_ENABLED=false` hasta verificar DNS/PTR/TLS y entrega controlada; las credenciales se generan y almacenan sólo en el VPS, sin pedirlas por chat. Mientras ese modo sea false, registro, reenvío y solicitud de recuperación quedan deshabilitados; cuentas confirmadas existentes pueden entrar. La disponibilidad vigente se comprueba en capabilities y en el manifiesto activo, no se deduce de este procedimiento de preparación. No crear confirmaciones o accesos por atajo.
- Protector PFX privado, key ring persistente, HTTPS y proxies exactos siguen siendo obligatorios sin correo. MFA TOTP es obligatorio para `Users.Manage`, `Content.Manage` y `Subscriptions.Manage`; niveles institucionales, permisos y suscripciones son independientes. Propietario protegido sólo mediante bootstrap explícito para una cuenta exacta confirmada y designada; su dirección configurada es privada. Sólo el propietario delega permisos, que son independientes del estado y niveles institucionales. Ningún otro gestor puede suspenderlo ni quitarle autoridad; el bootstrap no cambia contraseña, confirmación o MFA.
- Catálogo: Lecturas, Documentales, Videos, Podcast, Charlas online y Cursos. Metadatos y sinopsis públicas; borradores/archivados no se exponen. Obra completa y referencia YouTube se almacenan separadas y se sirven sólo a cuentas activas confirmadas con acceso vigente: Gratuito (`free_beta`) permite únicamente obras marcadas gratuitas; Probacionismo y Anual permiten todo el catálogo durante su periodo. Una marca gratuita no se hereda a los elementos de un curso o programa. Cursos ordenan obras y programas ordenan cursos; no añadir una séptima categoría. Publicación con concurrencia, slug estable y auditoría atómica.

## Validación y publicación

- Elegir QA por el riesgo real, no por número de líneas. Simple: texto/estilo/ergonomía frontend sin cambios de API, reglas, permisos, datos, dependencias o runtime; usar el certificado acotado `bash scripts/verify.sh --frontend-low-risk` sólo cuando su allowlist y la equivalencia con la versión publicada lo permitan. Medio: comportamiento de un módulo, con pruebas focales e integración/recorridos afectados; mientras no exista un certificador específico, la publicación usa el gate completo. Delicado: autenticación/MFA, permisos/acceso, suscripciones/pagos, datos/migraciones/concurrencia, secretos, dependencias o infraestructura; ejecutar el gate completo. Ante alcance dudoso, subir de nivel. Leer `docs/quality.md` para los controles y límites de cada procedimiento. Congelar el commit definitivo; las verificaciones deben corresponder a ese candidato limpio. No usar el gate como formateador ni repetir controles ya aprobados sin cambios o preocupaciones nuevas.
- QA usa recursos `acropolis_test_*`, credenciales/datos sintéticos, PostgreSQL real y CA/SMTP propios; nunca cargar `.env` productivo, montar datos de producción o el socket Docker. En este VPS compartido ejecutar una sola suite/carga pesada a la vez.
- Informes privados en `.local/qa/<sha>/<run>/report.json` del entorno que los ejecutó. Las pruebas WSL no trasladan certificados ni IDs de imágenes al VPS. Para publicar, el informe aceptado por deploy.sh y las imágenes exactas deben estar en el VPS; SHA e IDs de web/migraciones deben coincidir, con passed y deployment_eligible=true. No rebajar umbrales ni ignorar fallos. Las cargas con 100.000 cuentas/10.000 fichas y 50 sesiones/lectores no acreditan 1.000 concurrentes ni streaming.
- Cambios exclusivamente de instrucciones/documentación o de orquestación de QA, sin modificar aplicación, dependencias, imágenes ni configuración/migraciones de runtime, se validan por contenido, referencias, formato de skills, pruebas CLI y contratos administrativos afectados, preflight y revisión del flujo. No reconstruir ni volver a desplegar la aplicación sólo por esos cambios ni certificar una nueva imagen con esas comprobaciones. Mantener por separado el HEAD de instrucciones/herramientas y el SHA/IDs del runtime publicado; el siguiente cambio de aplicación requiere el certificador definitivo apropiado a su riesgo y un futuro despliegue exige el informe del SHA que deploy.sh acepta.
- Para preparar, revisar o ejecutar un despliegue aplicar acropolis-vps-deploy. Desplegar sólo si solicitado; una autorización vigente basta. La autorización del incremento ya publicado se agotó con esa entrega. El traslado de desarrollo a WSL no solicita otro despliegue ni activación. No inferir otras publicaciones por actualizar código, instrucciones o QA y conservar todas las precondiciones para una futura publicación autorizada.
- Dominio `https://acropolischannel.naperu.cloud`, Compose `acropolis-channel`, web8080, alias `acropolis-channel-web`, red externa `dokploy-network`. DB privada sin puerto del host y roles separados. `scripts/deploy.sh --expected-sha SHA` utiliza las imágenes aprobadas sin reconstruir.
- Routing exclusivamente en `/etc/dokploy/traefik/dynamic/acropolis-channel.yml`; conservar configuración global/ACME/otros routers. Verificar DNS, TLS normal, redirect, interfaz/API. Si una política bloquea el navegador, respetarla y declarar la revisión visual pendiente; no sustituirla con una automatización que eluda el bloqueo.

## Infraestructura y continuidad

Guardar las decisiones duraderas del propietario en este AGENTS o en la documentación versionada del módulo correspondiente; sincronizarlas mediante Git. El avance y pendientes se registran en `.local/continuation-current.md` del entorno en uso. WSL conserva el trabajo local; la continuidad y operación de producción permanecen en el VPS. Registrar decisiones útiles para retomar, no una copia indiscriminada de mensajes ni secretos.

- `.env`, `.local/`, claves, dumps y reportes son privados y no entran en Git/imágenes. Inspeccionar sólo datos necesarios sin mostrar contraseñas, semillas/QR/códigos MFA, enlaces de tokens ni configuración completa sensible.
- Preservar SSH administrativo, autenticación GitHub, otros proyectos, datos y volúmenes. No purgar Docker ni down-v producción. Respaldar DB, key ring, PFX y configuración conjuntamente; conservar recuperación de imagen/Compose/env/routing compatibles. No bajar migraciones automáticamente.
- Restaurar una base antigua exige web detenido, invalidación y revalidación explícita conforme a `docs/identity-operations.md` y `docs/mfa-operations.md`; no reactivar sesiones/credenciales/MFA del backup ni usar bootstrap como recuperación.
- Al cerrar o pausar, registrar commit/Git, informes, trabajo pendiente y procesos propios en `.local/continuation-current.md` del entorno en uso; actualizar la guía de acceso si corresponde. Registrar el runtime real únicamente tras consultarlo en el VPS, con fecha de comprobación. Consultar procesos/manifiestos del entorno correcto antes de repetir una operación interrumpida. Una QA cortada no certifica despliegue. Mantener el detalle administrativo de producción en `.local/vps-deployment.md` del VPS, sin duplicarlo en WSL ni en documentación pública.

Los planes y su alcance ya fueron confirmados el 7 de octubre de 2026. Quedan pendientes el proveedor/API de facturación, la intranet y reglas institucionales, migración y aceptación; no declarar completa la sustitución del sistema anterior por implementar sólo los planes.
